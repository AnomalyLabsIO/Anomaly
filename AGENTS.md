# AGENTS.md

This file is for coding agents working in this repository.

## Repository Overview

- Solution file: `Anomaly.slnx`
- Main projects:
  - `Anomaly.Client` - MelonLoader-based game client mod, `net6.0`, IL2CPP, HarmonyX. Owns the MelonMod entry point, Harmony patches, auth, diagnostics, file transfer, and internal state trackers. References `Anomaly.Client.Api` via ProjectReference.
  - `Anomaly.Client.Api` - public mod-facing API surface, `net6.0`, IL2CPP. Event buses, feature wrappers, registries/facades (CommandRegistry, ClientConfig, Scheduler, UiCanvas, etc.), and the `Anomaly.Client.Api.Events.*` + `Anomaly.Client.Api.Features.*` namespaces. No HarmonyX dependency. Third-party mods reference this DLL (and `Anomaly.Shared`), not `Anomaly.Client`.
  - `Anomaly.Server` - LabAPI server plugin, `.NET Framework 4.8`, Harmony
  - `Anomaly.Shared` - auth protocol + message DTOs + crypto, `.NET Framework 4.8`. Client, Client.Api, and Server only; the separate launcher repository deliberately does not reference it.
- Client user data lives in `%APPDATA%/Anomaly/` on Windows: `user.json`, `CrashReports/`, and per-mod `config.json` / `data.json`.
- Launcher and installer sources live in the sibling `anomaly-launcher` repository and have their own agent guidance and build/test commands.
- Root README covers user-facing install steps; internal conventions inferred from source.

## Build Commands

Run commands from the repository root unless noted otherwise.

- Build the SDK-style client project:
  - `dotnet build Anomaly.Client/Anomaly.Client.csproj -c Debug` (transitively builds `Anomaly.Client.Api`)
- Build the SDK-style client API project (standalone):
  - `dotnet build Anomaly.Client.Api/Anomaly.Client.Api.csproj -c Debug`
- Build the legacy server project:
  - `dotnet build Anomaly.Server/Anomaly.Server.csproj -c Debug` (or `msbuild` — the project is legacy-style but builds under either)

  - `dotnet build Anomaly.Shared/Anomaly.Shared.csproj -c Debug`
- Build the whole solution:
  - `msbuild Anomaly.slnx /p:Configuration=Debug`

## Build Caveats

- `Anomaly.Client` has many hard-coded local assembly references under a sibling reference-client install — these are `HintPath`s for IL2CPP-interop assemblies generated by MelonLoader. Expect build failures on fresh machines.
- `Anomaly.Server` and `Anomaly.Shared` reference local server/game DLLs via relative `..\..\Server\server\SCPSL_Data\Managed\...` paths. Also environment-specific.
- **Post-build deploy steps** (Client, Server, Shared) copy outputs into local game/server dirs via MSBuild `<Copy>` targets guarded by `Condition="Exists('$(...)')"`. If the target dirs don't exist on this machine, the build still succeeds — no copy happens. Override defaults with these MSBuild properties:
  - `AnomalyServerDir` (default: `..\..\..\Server\server`)
  - `AnomalyClientDir` (default: `..\..\..\Client`) — used by Shared only
  - `AnomalyClientModsDir` (default: `..\..\..\Client\Mods`) — used by Client only
- If a build fails because an external path doesn't exist on the current machine, document that rather than guessing replacements.
- `Anomaly.Client` sets `<EnableDefaultCompileItems>false</EnableDefaultCompileItems>`, so new `.cs` files must be added to the `.csproj` manually.
- `Anomaly.Server` and `Anomaly.Shared` also enumerate source files explicitly in their legacy project files. New `.cs` files here must be added to `<ItemGroup>` `<Compile Include=...>` lists.
- `Anomaly.Client.Api` is SDK-style with default compile-item inclusion — new `.cs` files compile automatically.
- `Anomaly.Client.Api` declares `[assembly: InternalsVisibleTo("Anomaly.Client")]` (see `Anomaly.Client.Api/Properties/AssemblyInfo.cs`) so Harmony patches in Client can call `internal` event invokers (`ClientEvents.OnSceneLoaded(...)` etc.) on public Api handler classes. The reverse direction is forbidden — Api never references Client types.

## Project Structure Conventions

- `Anomaly.Client.Api/` is the public mod-facing surface, organized by subsystem (`Commands/`, `Config/`, `Enum/`, `Features/`, `Input/`, `Localization/`, `Networking/`, `Persistence/`, `Scheduling/`, `UI/`, `Assets/`, `Components/`, `FileTransfer/`, `Events/` with `Args/` + `Handlers/` subfolders). Namespaces follow the folder layout: `Anomaly.Client.Api.Features.Player`, `Anomaly.Client.Api.Events.Handlers.ClientEvents`, etc.
- `Anomaly.Client.Api/Internal/` is private implementation of the Api (hidden behind `internal` + `InternalsVisibleTo("Anomaly.Client")`). Contains `Config/`, `Input/`, `Localization/`, `Persistence/`, `Scheduling/`, `UI/`, `Wrappers/PlayerRegistry.cs`, and the root-level `ModNamespace.cs` validator. No public types should live under `Internal/`.
- `Anomaly.Client/` is runtime-only — `Core.cs` (MelonMod entry), patches, auth, diagnostics, file transfer, internal state trackers, and bootstrap that raises Api events. Never exposes public types that mods consume; all public API lives in `Anomaly.Client.Api`.
- `Anomaly.Client/Auth` is client-side auth/session logic (identity keypair, handshake state).
- `Anomaly.Client/Patches` is Harmony patches against game/client code, grouped by target subsystem. Patches raise Api events by calling the `internal` `OnXxx` invokers on `Anomaly.Client.Api.Events.Handlers.*` static classes.
- `Anomaly.Client/Diagnostics` is crash/hang monitoring.
- `Anomaly.Client/Internal/{Bootstrap,Effects,Stats,Map,Round,Networking}` are bootstrap orchestration and state trackers reached only from patches — never from Api.
- `Anomaly.Server/Auth` is preauth/session state for server validation.
- `Anomaly.Server/Patches` is Harmony patches against server transport/auth flow.
- `Anomaly.Server/API/Plugins` is the server-side plugin discovery. The client side intentionally has no equivalent — `Anomaly.Client.Api` is a peer library that exposes events/helpers/wrappers for other mods to consume, and does not orchestrate their lifecycle.
- `Anomaly.Server/{Assets,FileTransfer,Round,Networking}` are server-authoritative bridges that relay state to clients over the Anomaly message channel (`0xFE`).
- `Anomaly.Shared/Auth` is protocol payloads and crypto helpers (ECDSA identity, X25519 handshake, AES-GCM).
- `Anomaly.Shared/Networking/Messages` is the full set of wire messages used between Client and Server.
- Keep new files in the folder whose namespace and responsibility already match.

## Namespace And File Layout

- Prefer file-scoped namespaces: `namespace Anomaly.Client.Auth;`
- Keep one primary type per file unless the surrounding pattern clearly differs.
- Match namespace to folder path.
- Keep `using` directives at the top of the file.
- Use aliases only when needed to resolve conflicts or clarify IL2CPP types.

## Imports

- The repo does not enforce strict alphabetical grouping, but keep imports tidy.
- Prefer a single contiguous `using` block.
- Remove unused imports when touching a file.
- Keep project-specific and third-party imports readable; do not churn import order unnecessarily.
- Preserve file-level aliases already in use.

## Formatting

- Use 4 spaces for indentation.
- Use braces in the standard C# K&R style.
- Short guard clauses may omit braces if the surrounding file already does that.
- Keep line length reasonable, but prioritize matching existing formatting in the file.
- Avoid opportunistic reformatting of unrelated lines.

## Naming

- Use `PascalCase` for classes, methods, properties, events, and public members.
- Use `_camelCase` for private static and instance fields.
- Use descriptive names for patch methods that reflect the hooked behavior.
- For DTO-like protocol types in `Anomaly.Shared/Auth`, preserve the existing field/property style of the type.
- Do not rename public protocol fields casually; they may be relied on across projects.

## Types And Nullability

- `Anomaly.Client` disables nullable reference types (matches the game's IL2CPP-generated assemblies).
- `Anomaly.Shared` and `Anomaly.Server` (legacy projects) do not enforce NRT.
- Do not introduce nullable-only style changes across older files unless needed for the task.
- Prefer explicit runtime null checks where the surrounding code does so.
- Use `var` when the right-hand side makes the type obvious.
- Use explicit types when they improve readability for game/network/crypto code.

## Fields, Properties, And Collections

- Static utility and patch classes are common; follow the file's existing pattern.
- Singleton-style accessors such as `Instance` and `Singleton` are used throughout the repo.
- Object initializers and target-typed `new()` are common in modern files.
- Avoid introducing collection expressions or newer syntax if it makes legacy-targeted files harder to maintain.
- Be careful when editing shared auth payload classes; wire format and field order matter.

## Error Handling

- Broad `try/catch` blocks are common around Harmony patches, auth boundaries, and runtime integration points.
- When catching exceptions, log enough context to diagnose failures in the mod/plugin environment.
- Prefer fail-soft behavior in patch entry points when the alternative is crashing the game/server hook.
- Do not swallow exceptions silently unless the file already uses an intentionally silent fallback.
- For validation failures, return or reject early instead of nesting deeply.

## Logging

- In client code, prefer `MelonLogger.Msg`, `MelonLogger.Warning`, and `MelonLogger.Error`.
- In server plugin lifecycle code (Plugin.cs, event handlers on the main thread), use LabAPI `Logger`.
- In server off-thread or preauth-heavy paths (Harmony patches on `ProcessConnectionRequest`, encryption path, anything invoked from Mirror/LiteNetLib worker threads), use `OffThreadLogger`. Do NOT call `GameCore.Console.AddLog` directly — it's not thread-safe and we've unified on `OffThreadLogger`.
- Match the logging style already used in the file instead of introducing a new abstraction.
- Keep logs actionable; include identifiers like endpoint, user ID, server identifier, or request type when relevant.

## Patches And Runtime Hooks

- Harmony patches are a core mechanism in both client and server projects.
- Keep patch methods minimal and defensive.
- Avoid expensive logic inside prefixes/postfixes unless necessary.
- If patch behavior depends on fragile upstream signatures, document that in code only when it is non-obvious.
- When modifying auth or network patches, cross-check against the external export directories before changing protocol assumptions.

## Auth And Protocol Safety

- Client and server auth flows are tightly coupled through `Anomaly.Shared/Auth`.
- Treat handshake/login payload layout as protocol code, not ordinary DTO cleanup territory.
- Preserve byte ordering, field sizes, and encode/decode symmetry.
- Any change in shared auth code should be reviewed for both client and server impact.
- Prefer additive instrumentation over behavior changes when debugging protocol issues.

## Legacy Project Notes

- `Anomaly.Server` and `Anomaly.Shared` use legacy MSBuild project files, not SDK-style defaults.
- Be conservative with language features even though `LangVersion` is set to `latest`.
- Avoid assuming all modern tooling works equally across the mixed project styles.
- If you add files to legacy projects, update the `<Compile Include=...>` entries manually.

## Cross-Project Scoping Rules

- The separate launcher/installer repository deliberately does not reference `Anomaly.Shared`; do not add that cross-repository dependency as part of core work.
